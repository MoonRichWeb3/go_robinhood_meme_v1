# 15 优质项目查询

- 最新更新时间：2026-09-02 14:51 (UTC+8)
- 适用范围：SQL 现算 + `[信号]`；`GET /signals`
- 来源：FR-07；底稿 §6.3–6.4
- 对应需求：FR-07
- 落地包：`internal/httpsvc` + store 查询；可选 `internal/app` 定时现算打日志

## 职责

不建 `project_signals` 表。用现有表回答三类问题；命中可打 `[信号]`；只读 HTTP 可列出。

## 边界

- 不预计算落表
- 不推送、不订阅
- 查询必须有时间窗与 limit（默认 50）
- 信号不是交易指令

## 三类定义（v0 定稿）

### 1. 聪明钱所发（级别 ≥ B）

`launch_index.creator_eoa` **或** `creator_contract` 能 join 到 `smart_wallets.address`，且该钱包 `level` ∈ {S,A,B}（按当前存档级别，不在查询时重算评分）。

不要求 status=active（已拉黑创建人仍可能算「曾是聪明钱所发」）。**v0 定稿：** 只认名单里 **仍存在** 的行；已删除地址无法 join，不出现。暂停/拉黑仍出现。

### 2. 开盘 1 小时内 ≥ 2 个有效聪明钱买入

对每个 `token_address`：

- 窗口：`[created_at, created_at+1h]`（UTC）
- 计入：`wallet_events.kind=buy` 且当时写入时已是聪明钱（表里的行即证明；**不**用当前名单回溯过滤掉已拉黑——历史买入行仍算人数）
- 去重钱包数 ≥ 2

「有效」指记账发生时的有效名单（已体现在行上）。当前已拉黑不影响历史计数。

### 3. 近 7 日高分且有新发盘

v0 **不算分数斜率**（无分数历史表，也不建）。命中条件：

- 近 7 日 `wallet_events.kind=launch` 至少 1 笔（受交易表 7 天保留约束）
- 当前 `score` ≥ 50（B 及以上）且 `score_sample_n` ≥ 8

HTTP `kind=score_launch`。日志规则名用 `高分新发盘`，**不要**写成「分数上升」。响应不必再加 `approx` 字段。

## GET `/signals`

Query：`kind=smart_launch|cluster_buy|score_launch`（必填其一）、`limit`。

响应：token 或 wallet 列表 + 命中原因中文字段 `reason`（API 可用中文值，键仍英文 `reason`）。

## 定时日志

可选：`RH_SIGNAL_INTERVAL_SEC` 默认 `3600`。每轮每类最多打 20 条 `[信号]`，避免刷屏。重复 token 同一天不必重复打（内存 LRU 有界 1000）。

`[信号]` 键：`时间`、`类型=信号`、`规则=`（聪明钱所发 / 开盘同买 / 高分新发盘）、`代币=` 或 `钱包=`、`盘口=`。

## 失败

SQL 超时：`[错误]`，本轮跳过。不要写信号表当补偿。

## 依赖

只读 SQL。禁止扫块路径里同步跑无界全表（定时器独立，有 LIMIT）。

## 验收

构造：B 级钱包创建 → kind1 命中。两钱包 1h 内买入同一新盘 → kind2。近 7 日有发盘且 score≥50、样本≥8 → kind3。无 `project_signals` 表。日志不要出现「分数上升」。

## 调研

无。
